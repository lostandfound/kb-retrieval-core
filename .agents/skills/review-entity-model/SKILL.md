# エンティティ設計レビュー

このスキルは、知識を追加・修正する前に「何を一つのエンティティとして表すか」を決めるために使う。出力はレビュー結果と実装候補であり、Markdown、index、graph、vocabulary、references は変更しない。型名、述語、タグ、本文セクションは導入先の語彙を正本とし、このスキルから固定の型体系を仮定しない。

以下の資料・作成者などの表現は対象の例であり、導入先にその型や分類が存在することを前提にしない。

## 準備

1. リポジトリの `kb-domain.yml` から `content_root` を確認する。
2. `AGENTS.md`、README、`<content_root>/vocabulary.yml` を読み、型・述語・タグの正本を確認する。型名や述語をこのスキル本文の固定リストで代用しない。
3. 対象エンティティ、候補に挙がった出典、同じ対象を扱いそうな title・alias・slug・本文リンク・relations を検索する。
4. 既存の `docs/CONCERNS.md` と `docs/BACKLOG.md` があれば、対象に関する未解決事項を読む。依頼がない限り書き換えない。

## 判断の順序

### 1. 対象の同一性

まず対象を一文で定義する。資料、人物、抽象概念、製品、出来事、メモなど、導入先で区別される異なる対象を一つのエンティティに混ぜない。

次を区別する。

- 出典として参照するだけの資料
- その資料自体を説明・比較・他ノードと接続したい知識対象
- 資料の作成者、組織、データセットなど、独立した知識対象になり得るもの
- 資料が説明する概念や実体

出典として使うだけなら `references.yml` で足りる。資料自体を知識対象として扱う必要がある場合だけ、正本の型から適切なエンティティを選ぶ。

### 2. 型の適合性

候補の型が、導入先の `vocabulary.yml` に定義された意味、必須フィールド、本文構成に合うかを確認する。スキル本文に型名を列挙せず、実際に存在する型定義を参照する。

- 型の定義が表す対象を一つだけ扱っているか
- 型固有のフィールドと本文セクションに無理がないか
- 一時的な記録用の型を恒久的な知識の代用品にしていないか
- 抽象概念と具体的な資料・実体を混同していないか
- 導入先が専用型を持つ対象を、より汎用的な型へ押し込んでいないか
- 一つのファイルを別の型へ移すより、二つ以上へ分割すべきではないか

型変更を提案する場合は、現在の型、候補型、型定義に照らした理由、移行時に失われる情報を示す。

### 3. ノード化の要否

すべての固有名詞をノード化しない。次の観点で、独立ノード、既存ノードへの記述、出典のみのどれが最小で十分かを決める。

- その対象について独立した説明を返す必要があるか
- 複数のエンティティから再利用されるか
- relations の始点・終点として検索や推論に使うか
- 独自の出典、時期、属性、限界を持つか
- ノード化してもほぼ名前だけにならないか

例えば、ある資料を単に引用するだけなら出典登録で足りるが、その資料自体の内容や位置づけを説明するなら、導入先の語彙に資料・成果物に対応する型があるかを検討する。資料の作成者も、独立した説明や複数の対象との関係が必要な場合だけ、導入先に対応する人物・組織等の型の候補にする。型が存在しない場合は、未定義の型を発明せず、既存本文・出典・別の既存型で表現できるかを検討する。

### 4. relation とタグ

relation は、語彙に定義された述語の意味・向き・型制約を満たす場合だけ提案する。グラフを密にする目的で `related-to` を追加しない。 `related-to` は未分類の印なので、始点と終点の型から語彙の標準述語（`part-of` / `derived-from` / `created-by` / `located-in` / `follows`）か、その下に `broader` で吊るされた述語に降りられないかを先に検討する。降りられないなら関連項目に関係の意味を一文で書く。新しい述語を提案するのは、既存の述語の下に `broader` で吊るせて、かつ検証器に弾かせたい型制約かその述語で絞る問い合わせがあるときに限る。複数の族に読める関係はより多くを含意する族に置き（親子は `follows` ではなく `derived-from` の下）、対称な関係（兄弟・婚姻など）はエッジにせず共有する親かハブ Concept で受ける。

本文中のリンクと frontmatter の relation は役割が異なるため、両方が必要かを確認する。

タグは検索・一覧上の有用な分類かを確認する。分類の不足を感じても、反復例や検索上の実害がない限り新しいタグを提案しない。

## 出力形式

対象ごとに、次を短く報告する。

```text
対象: <対象の一文定義>
推奨: <既存型 / 新規ノード不要 / 分割 / 統合 / 保留>
理由: <型定義・既存KB・再利用性に基づく理由>
relation: <提案する場合のみ、predicate・向き・target>
出典: <references.ymlだけで足りるか、エンティティのsourcesが必要か>
判断保留: <不足している根拠またはユーザー判断>
```

最後に、候補を `実装してよい`、`CONCERNS に送る`、`現状維持` のいずれかへ分類する。`CONCERNS.md` や `BACKLOG.md` への反映、エンティティ作成、型・タグ・述語の追加は、ユーザーが別途依頼した場合に `add-entity` や導入先の手順へ引き渡す。

## しないこと

- titleやembeddingの類似だけで統合・削除を決めない
- 孤立ノードを不要とみなさない
- 著者・組織・引用先を機械的に全件ノード化しない
- relation数、タグ数、カテゴリ均衡を品質指標にしない
- 本文を自動要約・自動リライトしない
- レビュー中に `index.md` や `graph.json` を手編集しない
