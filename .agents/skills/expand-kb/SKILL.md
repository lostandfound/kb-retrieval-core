# KB 拡張ループ

導入先の規約とドメイン判断を正本とし、ハーネスは共通の進行だけを担う。

## 準備

`kb-domain.yml` から `content_root` を解決し、README、CONTRIBUTING、`vocabulary.yml` と、導入先が指定する収録方針・拡張方針を読む。任意の予約運用ファイル `docs/CONCERNS.md` と `docs/BACKLOG.md` は、存在する場合だけ利用し、依頼されていない限り新設しない。

作業ツリーを確認し、既存の変更を拡張作業へ混ぜない。利用できるコマンドは `kb --help` と各サブコマンドの `--help` で確認する。

## 候補を決める

検証結果、グラフの孤立・疎な関係、RAG 評価の未解決ギャップ、本文中の未リンク言及、`docs/CONCERNS.md`、`docs/BACKLOG.md` から候補を集める。外部探索は導入先の方針または専用ツールがある場合だけ行う。

候補を次に分類する。

- 未収録エンティティ
- 不足する relation
- 不足・不整合のある本文
- description、tags、リンクなどの検索性
- 未確定または競合する主張（Claim 候補）

利用者への効果、既存知識との接続、根拠の入手可能性を基準に小さなバッチを選ぶ。件数や型の優先順位は導入先の拡張方針に従う。候補選定だけを依頼された場合は、実装せず結果を報告するか、既存の `docs/BACKLOG.md` へ記録する。

## 調査・実装

導入先の出典規約、型・述語・タグ語彙、収録基準を守る。新規エンティティには `add-entity` スキルを使う。確定できない関係や値を通常の本文・relationへ押し込まず、導入先が Claim を使う場合は Claim として記録する。解消先がまだ分からない違和感は、既存の `docs/CONCERNS.md` があればそこへ残す。

並列作業やサブエージェントは前提にしない。利用可能で作業分割に実益がある場合だけ使い、最終的な規約適合と統合は実行主体が確認する。

## レビューと完了

変更した範囲について、少なくとも次を確認する。

- frontmatter、型、述語、relation の向き、タグ、リンクが導入先の契約に従う
- 出典が実在し、本文の主張を実際に裏付ける
- 競合説や単一源の主張が、導入先の確度・Claim方針に従っている
- 既存エンティティとの矛盾やRAGの退行を生んでいない

`kb validate` と `kb sync --check` を基本とし、導入先が定めるテストと評価も実行する。コミットやpushは、ユーザーの依頼または導入先の明示的な運用に含まれる場合だけ行う。

`docs/BACKLOG.md` に対応項目がある場合は、実装と検証が完了した後にだけ消し込む。運用がコミットハッシュを要求する場合、対象コミットと同じコミットへ自己参照を書かず、後続の文書更新で記録する。作業中に見つけた別件は今回の変更へ混ぜず、既存の `docs/CONCERNS.md` または `docs/BACKLOG.md` の役割に応じて記録する。
