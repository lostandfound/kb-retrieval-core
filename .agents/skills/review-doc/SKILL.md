文書は「誰が・何を知るために開くか」で役割が決まり、役割に合わない内容は正しくても害になる。行ごとの正誤より先に、文書全体を役割に照らして判定する。

## 手順

1. **役割を先に確定する。** 本文を読む前に、ファイル名・置き場所・冒頭 3 行・他文書からの参照のされ方から、想定読者と「読者がこの文書で得るべきもの」を 1 文で書く。下の対応表を基準にし、対応表にない種別は自分で定義して明記する。
2. **節ごとに役割適合を判定する。** 各見出し（`##` 単位）について、役割に「合う／混在／外出し」の 3 値で判定する。判定は必ず全節に付ける。`###` 小節は親の `##` に含めて判定し、小節だけ判定が親と異なる場合に限り小節を別行で挙げる。判定の優先順位は (a) 別ファイルの正本の写しなら「外出し（参照に置換）」、(b) 正本はないが役割外の内容（設計の背景・計画・内部説明）が節の主体なら「外出し」、(c) 役割に合う内容に役割外の段落が混じるなら「混在」、(d) それ以外は「合う」。(a) と (b) の両方に当たる節は (a) で判定し、正本を示す。
3. **正本との重複を探す。** 節の内容が別のファイル（スキーマ、`--help`、他の文書）の写しなら、正本を特定し「参照 1 行に置換」を提案する。写しは正本の更新に追随せず陳腐化する。
4. **内部語彙を拾う。** 想定読者が初見で意味を取れない語（社内・プロジェクト内のフェーズ名、ツール名の略称、エージェント名、進行中の計画に依存する表現）を列挙し、言い換えか説明かリンクかを示す。
5. **最後に内容の正誤・構造を見る。** 行番号付きの指摘は、1〜4 で「合う」と判定した節に限って行う。外出しや削除を提案した節の誤字・段落構成は指摘しない（消える内容を磨かない）。

## 文書種別と役割の対応表

| 種別 | 想定読者 | 得るべきもの | 置いてはいけないもの |
| --- | --- | --- | --- |
| README | 初見者（読む側・書く側の両方） | これは何か、最初にやること、詳細への地図 | 規約の本文、ツール一覧の写し、運用手順、ロードマップ |
| CONTRIBUTING | 編集に参加する人 | 従うべき規約と検証手順 | 設計の背景や議論、ツールの内部説明、進行中の計画 |
| AGENTS.md / CLAUDE.md | エージェント | 正本の所在と検証コマンドへの最短導線 | 規約や手順の本文（正本を指す） |
| 方針書（policy） | 設計判断をする人 | なぜその設計か、判断基準、非目標 | 手順の詳細、完了済み作業の未来形記述 |
| 計画書（plan） | 実装する人 | 段階、完了条件、現状 | 規約（完了後は規約側へ移す） |
| 運用文書（loop / ledger / backlog） | 周期作業をする人 | 手順、判定基準、記録 | 設計の背景（方針書へ） |
| スキル / エージェント定義 | エージェント | 確定的な手順と判断基準 | 規約の値の写し（正本を指す） |
| パッケージ README | パッケージ利用者 | インストール、CLI、提供資産 | 導入先リポジトリ固有の事情 |

## 報告形式

以下の順で書く。順序を変えない。

1. **役割**: 想定読者と得るべきものを 1 文。既存の冒頭がそれを言えていなければ、その旨を先頭に書く。
2. **節ごとの判定**: `節見出し — 合う／混在／外出し — 理由（外出し先または正本）` を全節分。
3. **内部語彙**: `語 — 出現行 — 対処（言い換え／説明／リンク）`。
4. **内容の指摘**: `行番号: 指摘 — 修正案`。「合う」節に限る。
5. **最小の第一歩**: 実施するなら最初に何を動かすかを 1 つだけ書く。

## よくある失敗

| 失敗 | 何が起きるか |
| --- | --- |
| 役割を決めずに読み始める | 行単位の指摘は出るが、節が丸ごと不要であることに気づかない |
| 役割の判定を最後に付け足す | 判定が指摘の後付け説明になり、指摘の取捨に使われない |
| 正本の写しを「抜けがある」と指摘して補完を提案する | 写しが増え、次の陳腐化点が増える。正しい対処は参照への置換 |
| 内部語彙を「文脈で分かる」と見逃す | 初見者の読者が最初に脱落する箇所を放置する |
| 外出し候補の節の誤字や構成を直す | 消える内容に工数を使う |
| 目次やアンカーの追加を最初の提案にする | 長さの原因（混在）を温存したまま導線だけ増やす |

## 使わない場面

- エンティティ本文・コラム・翻刻などコンテンツの校閲（文体や史実の確度は別の考証・執筆規範で扱う）
- 複数文書の相互整合の一括監査（audit-harness を使う。本スキルは 1 文書の内側を見る）
